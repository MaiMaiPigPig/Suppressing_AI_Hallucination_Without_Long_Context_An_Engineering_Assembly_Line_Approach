# 缺陷单-V0.6-003：需求 V0.6-001 与 V0.6-002 冲突

**发现人**：测试 AI

## 缺陷 1：仓库性质矛盾

**严重程度**：🔴 阻塞

### 问题描述

001 和 002 对拆分后的仓库性质给出了互相矛盾的描述：

| 条款 | V0.6-001 | V0.6-002 |
|------|----------|----------|
| 验收描述 | "上架仓库可独立 git clone 并正常运行"（第45行） | "纯本地、无远程、无历史提交"（背景段） |
| 隐含含义 | 仓库需要能被远程克隆（意味着需要 push 到远端） | 完全是本地操作，不涉及任何远程 |

002 在背景段说自己是"经人工补充与澄清后"的产物，但没有明确声明 001 已被替代或废弃。两份文档同时存在于当前工程目录中，开发无从判断以哪个为准。

### 影响

如果开发按 001 执行，会尝试配置远程仓库、push、clone 验证；按 002 执行则不需要。两条路径完全不同且不可调和。

### 产品决策

**以 V0.6-002 为准**。001 标记废弃。

### 处理结果

✅ 已解决。001 已从当前工程目录中删除，仅保留 002，冲突源消除。

## 缺陷 2：工具链归属冲突

**严重程度**：🔴 阻塞

### 问题描述

| 条款 | V0.6-001 | V0.6-002 |
|------|----------|----------|
| package.json 等 | 归应用仓库（第7-10行） | 归开发文档仓库（方案 B，备注段） |
| 应用仓库内容 | "TableChronicle/ 全部内容 + 工具链配置" | "仅 TableChronicle/ 应用本体" |

001 把 ESLint/TypeScript 工具链放在应用仓库里，002 把它挪到了开发文档仓库。这直接影响验证方式——001 的验收标准"上架仓库 npm install 无报错"在 002 的方案 B 下被明确放弃。

### 影响

开发如果混合参考两份文档，可能在仓库1放了不该放的工具链，或在仓库2遗漏了工具链。

### 产品决策

**以 V0.6-002 为准**：工具链归仓库2，仓库1为纯应用本体。

### 处理结果

✅ 已解决。001 已删除，冲突源消除；002 已统一为方案 B。

## 缺陷 3：验收标准体系不同

**严重程度**：🟠 中等

### 问题描述

001 有 7 条验收标准（第45-51行），002 改为 3 条人工准绳 + 每卡独立验收。两条体系的对应关系不透明——001 的验收标准 1~7 哪些在 002 中仍有效、哪些被覆盖或废弃？没有说明。

| 001 验收标准 | 002 是否覆盖 |
|-------------|:--:|
| 上架仓库可独立 git clone | ❌ 废弃（纯本地） |
| 开发文档仓库可独立 git clone | ❌ 废弃（纯本地） |
| .gitignore 各自正确 | ❓ 部分（改由卡 A/B 的专用 .gitignore 承接） |
| 缓存不进新仓库 | ❓ 卡 A/B 范围段提及但未列为独立验收 |
| 上架仓库无开发文档 | ❓ 隐含在范围的"仓库1仅 TableChronicle" |
| 开发文档仓库无运行时代码 | ❓ 隐含在范围的"仓库2 为开发资产" |
| npm install 无报错 | ❌ 明确放弃 |

### 影响

测试执行时不知道该按哪套验收标准做验证。

### 产品决策

**以 V0.6-002 的验收准绳 + 卡级验收为准**，001 的 7 条验收标准全部废弃。

### 处理结果

✅ 已解决。001 已删除，唯一验收标准为 002 的三条准绳 + 卡级验收。

## 缺陷 4：文档自身类型定义混乱

**严重程度**：🟠 中等

### 问题描述

V0.6-002 文件名使用 `需求-V0.6-002`（需求单前缀），但文件名后缀写的是"任务卡"，内容也拆成了"卡 A / 卡 B / 卡 C"的任务卡结构。

按模板规范：需求单是"需要写代码实现的功能需求"，任务卡是"开发执行前的准备工作"。V0.6-002 的仓库拆分需要写代码吗？不需要。它是规划性的任务拆解——应归为任务卡。

但实际上，仓库拆分本身是功能需求（拆仓库是一项工程决策），所以用需求单前缀也可以自洽。问题出在：**一个文件挂两个类型，让人困惑**。

### 产品决策

人工已裁定维持现状，不对类型定义做变更。
