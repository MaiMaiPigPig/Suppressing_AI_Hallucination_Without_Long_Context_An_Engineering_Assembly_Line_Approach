## 一、范围

- **做**：
  1. 在 `TableChronicle\` 内 `git init`，建立仓库1（应用工程），编写专用 `.gitignore`，首次提交
  2. 在项目根目录 `git init`（新建，不复用旧 `.git`），建立仓库2（开发文档与工具链），编写专用 `.gitignore`，纳入：`开发资源\`、`测试脚本\`、`package.json`、`package-lock.json`、`eslint.config.mjs`、`jsconfig.json`
  3. 验证准绳②：仓库1 程序正常启动（Flask 5001），首页、车卡页、数据加载正常
  4. 验证准绳③：`csv转json.py` 跨仓库产出 JSON 到仓库1；`车卡_回归测试.py` 通过 HTTP 对仓库1 执行；ESLint 跨仓库检查仓库1 JS 代码
  5. 仓库1 和仓库2 全部验收通过后，删除旧根目录 `.git`（卡C 破坏性操作）
- **不做**：
  1. 不修改任何业务代码（`TableChronicle\` 内 Python/JS/HTML/CSS 一行不改）
  2. 不修改 `csv转json.py` 的数据转换逻辑（如路径需调整，仅改 `JSON_DIR` 路径常量，不改算法）
  3. 不修改 `车卡_回归测试.py` 的测试逻辑（Selenium 走 HTTP，不受目录影响）
  4. 不配置远程仓库（纯本地，无 remote、无 push）
  5. 不迁移 Git 历史（全新 `git init`，旧历史随旧 `.git` 废弃）

## 五、实现步骤

### 阶段 1 — 卡 A（仓库1）与卡 B（仓库2）并行

#### 1.1 卡 A：建立仓库1

1. 进入 `f:\跑团工具\TableChronicle\`
2. `git init`
3. 创建 `.gitignore`（内容见 二、改动清单）
4. `git add .`
5. `git status` 人工检查，确认无 `__pycache__`、`.pytest_cache` 等被纳入
6. `git commit -m "初始化仓库1：应用工程"`
7. 启动 `python app.py`，确认 Flask 5001 正常启动（控制台无 traceback）
8. 浏览器访问首页（`http://localhost:5001`），确认页面正常渲染、无白屏；进入车卡页，确认选项列表和数据加载正常（浏览器控制台 F12 无红色报错、Network 面板无 404/500）；如肉眼判断无异常即通过
9. **卡 A 检查点**：A1 ✅ / A2 ✅ → Git 提交完成

#### 1.2 卡 B：建立仓库2

1. 确保不在旧 `.git` 目录范围内（如旧 `.git` 存在，先 `ren .git .git_old` 临时改名）
2. 在 `f:\跑团工具\` 根目录 `git init`
3. 创建 `.gitignore`（内容见 二、改动清单）
4. `git add .`
5. `git status` 人工检查，确认无 `TableChronicle/`、`node_modules/`、`.vscode/`、`__pycache__/`、`.pytest_cache/` 被纳入
6. `git commit -m "初始化仓库2：开发文档与工具链"`
7. **卡 B 检查点**：B1 ✅ → Git 提交完成

### 阶段 2 — 准绳③联动验收

#### 2.1 B2：数据生产链路（csv → json）

1. 确保仓库1 Flask 未占用文件锁
2. 运行 `python 开发资源\data\csv转json.py`
3. 检查 `TableChronicle\data\json\` 下文件更新时间，确认 JSON 正常产出
4. 抽查 2-3 个 JSON（如 `classes.json`、`feats.json`、`spells.json`），确认内容非空、结构正常

#### 2.2 A3/B3：回归测试链路

1. 启动仓库1：`python TableChronicle\app.py`
2. 另开终端运行：`pytest 测试脚本\车卡_回归测试.py -v -s`（有头模式）
3. 确认全流程 17 步通过

#### 2.3 B4：代码检查链路（ESLint）

1. 在根目录（仓库2）运行 `npx eslint TableChronicle\`（或 `eslint.config.mjs` 配置的等效命令）
2. 确认 ESLint 正常扫描仓库1 JS 文件，输出结果无误报路径错误

### 阶段 3 — 卡 C：废弃旧仓库

**前置：** 以上 A1/A2/A3/B1/B2/B3/B4 全部通过。

1. 确认仓库1 `git log` 至少有 1 条提交
2. 确认仓库2 `git log` 至少有 1 条提交
3. 删除旧根目录 `.git`（如未重命名则直接删，如已临时改名为 `.git_old` 则删 `.git_old`）
4. 在根目录运行 `git status`，预期报错或提示不在仓库内（C1）
5. 进入 `TableChronicle\` 运行 `git status`，预期正常显示仓库1 状态（C2 一部分）
6. 人工确认文件完整性：`dir TableChronicle /AD` 和 `dir 开发资源 /AD`，与记忆中的目录结构对比，确认无文件丢失；抽查 `TableChronicle\app.py`、`开发资源\data\csv转json.py` 等关键文件仍存在（C3）
7. **卡 C 检查点**：C1/C2/C3 ✅

## 六、风险与应对

| # | 风险 | 发生场景 | 应对 |
|---|------|----------|------|
| 1 | **仓库2 .gitignore 漏排**：`TableChronicle\` 或 `node_modules\` 意外被 add | B-4 `git status` 时不仔细检查 | 首次 `git add .` 后必须 `git status` > 人工肉眼确认无异常目录 > 才 commit |
| 2 | **csv转json.py 跨仓库路径断裂** | 拆分后两仓库目录关系变化（如仓库1/仓库2不在同一父目录） | 当前设计两仓库在同一父目录 `f:\跑团工具\`，路径 `../../TableChronicle/` 理论不变。如实测失效，改 `JSON_DIR` 为绝对路径或相对路径修正 |
| 3 | **ESLint 找不到仓库1 文件** | `eslint.config.mjs` 的 files/ignores 默认扫描当前目录，仓库1 的 `TableChronicle\` 在文件系统上可见，但 ESLint 可能默认 excludes `.*` 目录或 node_modules 同级的 ignore | 实测 `npx eslint TableChronicle\`，如有路径问题则在 `eslint.config.mjs` 中显式配置 files 或运行参数 |
| 4 | **旧 .git 删除后发现仓库1或仓库2有遗漏文件** | 卡C 执行后才暴露 | 严格按"先建后验再删"原则，卡C 前必须 A+B 全部验收通过；仅删除 `.git` 目录，源代码文件完整保留，可随时重新 `git init` |
| 5 | **node_modules 意外纳入仓库2** | gitignore 写错或未生效 | B-3 `git status` 时重点检查，如出现 `node_modules/` 在暂存区，修改 gitignore 后 `git rm -r --cached node_modules` 再 commit |
