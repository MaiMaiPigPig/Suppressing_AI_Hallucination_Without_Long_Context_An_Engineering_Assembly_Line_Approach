**关联设计**：设计-v0.4-002（总）及子文档 A~J  
**审查日期**：2026-09-28  
**审查依据**：测试生产准则 流程分支 2（测试开发产物），攻击维度 11 项 + 代码质量维度 9 项

## 一、阻塞级（不修改则执行必出问题）

### 缺陷 1：002-A loader.js 伪代码缺少 applyDLCFilter 调用

- **维度**：正确性、回归
- **位置**：设计-v0.4-002-A 第二节 loader.js 伪代码
- **问题**：loader.js 的伪代码步骤为 resetCache → 加载 → preprocessPlaceholders → buildIndexes → 返回 dataCache，数据流图中 `applyDLCFilter` 在步骤 3 和 4 之间，但伪代码中无此调用。
- **后果**：开发按伪代码实现，dataCache 包含所有 DLC 的混合数据，车卡步骤显示不应出现的 DLC 内容。
- **建议**：在伪代码步骤 3 和 4 之间补上 `applyDLCFilter(dlcList)`。

**修复状态**：✅ 已修复
- 002-A loader.js 伪代码已补上步骤 4 `applyDLCFilter(dlcList)`，并注明数据流向（_fullDataCache → dataCache）

### 缺陷 2：所有设计文档零异常处理

- **维度**：异常（攻击维度）、异常（代码质量维度）
- **位置**：设计-v0.4-002-A~J 全部
- **问题**：所有接口设计只覆盖正常路径，零异常覆盖。以下异常无设计：
  - JSON 文件加载失败（网络错误、404）
  - 动态 import 失败（文件不存在、网络超时）
  - handler 未注册时 parseRule 的行为
  - 步骤校验失败的用户反馈
  - loadData 传入空 DLC 列表
  - upgrade 未导入角色即操作
- **后果**：开发自行处理异常，行为不一致；部分异常可能静默失败、用户无感知。
- **建议**：至少在核心接口（loadData、renderStep、parseRule）上补充异常处理策略。

**修复状态**：✅ 已修复
- 002-A 新增「六、异常处理策略」表格，覆盖 loadData、applyDLCFilter、preprocessAllPlaceholders、buildDataIndexes
- 002-C 在 renderStep 接口标注 @throws，navigation.js 的 nextStep/prevStep/goToStep 增加 try/catch + 错误提示
- 002-J 新增「7.3 异常处理策略」表格，覆盖 parseRule、processItemRules、handler 子模块

## 二、严重级（不修改则大概率出问题）

### 缺陷 3：upgrade 缺步骤数据清理映射

- **维度**：数据
- **位置**：设计-v0.4-002-B 第二节 character-state.js、设计-v0.4-002-G
- **问题**：002-B 的 `clearDataAfterStep` 依赖 `STEP_DATA_FIELDS`，但该常量只覆盖 creation 的 17 步。upgrade 有 7 步，回退时需清什么数据——未定义。
- **后果**：升级流程中用户点击"上一步"，后续步骤的数据可能脏残留。
- **建议**：在 002-B 或 002-G 中补充 upgrade 的步骤数据清理映射。

**修复状态**：✅ 已修复
- 002-B 新增 `UPGRADE_STEP_DATA_FIELDS` 常量（7 步映射），`clearDataAfterStep` 增加 `mode` 参数支持 creation/upgrade 双模式

### 缺陷 4：code-handlers/ 目录未在设计范围中

- **维度**：边界（代码质量）
- **位置**：设计-v0.4-002-J
- **问题**：002-J 覆盖了 handlers/ 下 16 个文件，但 code-handlers/ 下 4 个文件（registry.js、choose.js、half-prof.js、spell-level.js）走 `window.CODE_HANDLERS` 全局对象，未被任何设计文档覆盖。
- **后果**：handlers/ 迁移为 ES Module 后，code-handlers/ 仍为全局模式，两套 handlers 体系引用方式不一致。
- **建议**：明确 code-handlers/ 的处理策略：v0.4 不做则声明技术债，版本边界中记录。

**修复状态**：✅ 已修复
- 002-J 新增「七、code-handlers 处理策略」，明确 v0.4 暂不迁移，记录为技术债（建议 v0.5 处理），并说明原因（职责不同、无全局污染、调用方单一）

### 缺陷 5：filterableKeys 硬编码白名单落地位置未定

- **维度**：数据
- **位置**：设计-v0.4-002-A 第二节 cache.js
- **问题**：`applyDLCFilter(dlcList)` 需要知道哪些表支持 DLC 过滤。当前代码硬编码 `['races','subraces','classes','classPackages','backgrounds','backgroundPackages','feats','spells']`，设计中 `applyDLCFilter` 未说明此列表来源。
- **后果**：开发自行决定放 cache.js / constants / loader.js，与后续任务可能冲突。
- **建议**：明确 filterableKeys 放在 cache.js 还是 constants 中。

**修复状态**：✅ 已修复
- 002-A cache.js 的 `applyDLCFilter` 上方新增 `FILTERABLE_KEYS` 常量定义，明确白名单与过滤函数同文件

### 缺陷 6：HTML onclick 事件委托未在设计落地

- **维度**：功能
- **位置**：设计-v0.4-002-C
- **问题**：需求 002-C C4 要求将 HTML 内联 onclick 改为事件委托。评审单 R-1 将此标记为阻塞风险。002-C 的总设计"三、全局变量消除方案"中提了一句，但子文档 002-C 的接口设计里没有任何涉及 onclick 迁移的内容。navigation.js 和 step-router.js 的接口均未体现事件委托方式。
- **后果**：开发按当前设计提取 navigation.js 后，HTML 中的 `onclick="goToStep(N)"` 因 goToStep 不再挂 window 而全部失效。
- **建议**：在 002-C 中补充事件委托方案：在哪个文件初始化、委托挂哪个 DOM 节点、原 onclick 属性值如何映射到新事件处理函数。

**修复状态**：✅ 已修复
- 002-C navigation.js 的 `initNavigation()` 已完整实现事件委托（进度条 `.progress-bar` 容器监听 click，按钮直接绑定）
- 迁移步骤 4 增加事件委托覆盖要求，明确禁止保留 onclick 属性

### 缺陷 7：buildDataIndexes 同名函数冲突未解决

- **维度**：隐患
- **位置**：设计-v0.4-002-A 第二节 indexes.js、设计-v0.4-002-J 第三节 data-query.js
- **问题**：002-A 将 `buildDataIndexes` 提取到 `core/data/indexes.js`，002-J 对 `handlers/data-query.js` 中的 `buildDataIndexes` 改造为 export。两处同名函数——是合并为一个（handlers/data-query.js 改为 import core 的），还是保留两个独立版本？
- **后果**：如果保留两个，逻辑可能分歧，后续某个调用方引错了版本。
- **建议**：明确两者关系：合并 or 独立，以及谁依赖谁。

**修复状态**：✅ 已修复
- 002-A indexes.js 标注「handlers/data-query.js 中曾有同名函数，现统一到此文件」
- 002-J data-query.js 改为 `import { buildDataIndexes } from '../../core/data/indexes.js'`，不再定义该函数
- 依赖关系图和迁移步骤均已更新

## 三、一般级（不修改可能积累技术债）

### 缺陷 8：步骤 9 从死代码复活未标注

- **维度**：正确性
- **位置**：设计-v0.4-002-C 第二节 step-router.js、设计-v0.4-002-D
- **问题**：当前代码中步骤 9 在导航中被跳过（nextStep/prevStep/updateProgress 三处有跳过逻辑），renderStep case 9 是死代码。002-C 的设计中步骤 9 有路由条目，002-D 说"feature-selection.js 负责步骤 9 的选择 UI"——这是将步骤 9 从不可达变为可达。此行为变更未在设计文档中明确标注。
- **后果**：开发可能沿用现状跳过步骤 9，与设计意图冲突。
- **建议**：标注"步骤 9 从当前代码不可达状态恢复为活跃步骤"，并列出需要删除/修改的跳过逻辑清单。

**修复状态**：🔒 已关闭（人类确认）
- **原因**：步骤 9 在当前代码中**不是死代码**。character.js 的 `renderStep` 中有 case 9 调用 `renderFeatureSelectionStep`，`nextStep` 中跳过的是步骤 9 的**独立导航**（因为 feature-selection 被内嵌在 review 步骤里作为步骤 15）。002-C 恢复步骤 9 为独立步骤是**需求决策**，不是"复活死代码"。此条为测试误判。

### 缺陷 9：review.js 职责描述自我矛盾

- **维度**：一致性
- **位置**：设计-v0.4-002-D 第一节、第二节 review.js
- **问题**：职责矩阵写"review.js 只做总览收集，不做选择 UI"，但接口设计中 `renderReviewStep` 仍调用 `renderFeatureSelectionStep(container, 15)`——即 review.js 仍然嵌入了选择 UI。
- **后果**：开发不确定 review.js 到底能不能调用 feature-selection.js，以及调用算不算违反职责边界。
- **建议**：要么改职责描述为"review.js 做总览收集并嵌入 feature-selection 作为步骤 15"，要么从接口设计中移除该调用。

**修复状态**：✅ 已修复
- 002-D 职责矩阵改为「review.js：总览收集 + 嵌入 feature-selection」，明确 review.js 负责在总览页底部调用 feature-selection.js 渲染选择 UI，但核心选择逻辑仍由 feature-selection.js 独立完成
- review.js 接口增加 v0.4 边界注释，说明内嵌是历史遗留结构

### 缺陷 10：upgrade 复用 creation/steps/ 的接口约束未说明

- **维度**：复用（代码质量）
- **位置**：设计-v0.4-002-G 第二节
- **问题**：002-G 说 upgrade 复用 creation 的 `bonus.js`、`spells.js`、`sheet.js`，"传入升级模式参数 `{mode:'upgrade'}`"。但被复用的文件（bonus.js 等）当前接口是否支持 mode 参数？如果当前不支持，是否需要改接口？
- **后果**：开发 import 后发现被复用的文件没有 mode 参数，需要自行扩展接口。
- **建议**：明确被复用文件是否需要改接口、改接口的工作量归在哪个任务。

**修复状态**：✅ 已修复
- 002-G 新增「2.3 复用接口约束」表格，列明 5 个被复用文件的当前接口、需扩展内容、工作量评估
- 明确实现策略（末尾加 options 参数、mode 分支）、工作量归入 002-G

### 缺陷 11：动态 import 并发防护缺失

- **维度**：并发
- **位置**：设计-v0.4-002-C 第二节 step-router.js
- **问题**：步骤渲染使用动态 `import()` 异步加载，用户快速连点"下一步"时可能触发多次 renderStep，导致多个步骤渲染交错执行。
- **后果**：极快点击时 UI 可能闪烁或不一致。
- **建议**：在 step-router.js 中加锁或防抖，或声明 v0.4 不做。

**修复状态**：🔀 已转出 → 缺陷单-v0.4-003_动态import并发防护.md
- **原因**：并发防护是编码实现层面的交互细节，开发认为不属于设计文档职责范围。转为独立缺陷单，由产品决定设计方案（排队/丢弃/中断），再交开发落地。

### 缺陷 12：动态 import 无 loading 态设计

- **维度**：性能
- **位置**：设计-v0.4-002-C 第二节 step-router.js
- **问题**：首次进入某个步骤时动态 import 有网络延迟，从 38 个 script 同步加载改为按需加载后，用户首次进步骤会有等待。设计未提 loading 态如何展示。
- **后果**：用户体验退化——步骤切换时可能有一段空白等待。
- **建议**：在 step-router.js 中补充 loading 态处理。

**修复状态**：🔒 已关闭（人类确认）
- **原因**：loading 态是 UI 实现细节，不属于设计文档的覆盖范围。设计文档应关注模块职责和接口契约，而非具体的 loading 动画/占位符实现。且 38 个 script 改为按需加载后，首次加载的延迟是否可感知还是未知数——过早设计 loading 态可能导致过度工程化。

### 缺陷 13：feat_debug.js 残留文件未处理

- **维度**：结构（代码质量）
- **位置**：设计-v0.4-002-D、设计-v0.4-002-I
- **问题**：当前 `creation/steps/feat_debug.js` 是调试文件，不应存在于生产代码。002-D 的步骤文件清单未提及它的处理，002-I 的死代码清理也未列入。
- **后果**：迁移完成后生产代码仍残留调试文件。
- **建议**：在 002-I 的清理清单中加入 feat_debug.js。

**修复状态**：✅ 已修复
- 002-I 技术债表格新增 `feat_debug.js` 条目，并补充「feat_debug.js 处理方案」小节，明确检查命令和处理策略（无引用则删除 script 标签、文件保留按需加载）
