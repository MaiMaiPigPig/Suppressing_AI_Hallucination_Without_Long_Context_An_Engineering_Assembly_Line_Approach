### 3.2 迁移策略

**阶段 1（提取 core/ 层）**：
1. 在 `core/data/cache.js` 中定义 `let dataCache = {}; let _fullDataCache = {};`
2. `creation/character.js` 和 `upgrade/upgrade.js` 删除自己的定义，改为 `import { dataCache, _fullDataCache } from '../core/data/cache.js';`
3. 其他全局变量同理

**阶段 2（handlers 调整）**：
1. `handlers/index.js` 改为注册表模式，导入所有 handler 子模块
2. `handlers/data-query.js` 的函数改为 `export function buildDataIndexes() {...}`
3. `character.html` 和 `upgrade.html` 删除 `<script>` 标签加载 handlers，改为在 `app.js` 中 `import` 注册表

## 七、风险与设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| `dataCache` 用 `export let` 还是 `export const` | `export let` | 运行时会被重新赋值（加载新数据时），`const` 不可行 |
| `character` 用 `export let` 还是封装 API | `export let`（v0.4） | 需求明确不改调用方式，v0.5 再封装 set/get API |
| handlers 用注册表还是保持扩展模式 | 注册表（推荐） | 便于模块化管理，但保留扩展模式作为备选方案 |
| HTML 改为 ES Module 还是保留 script 标签 | 保留 script 标签（v0.4） | 降低风险，core/ 层用 module，页面层逐步过渡 |
| upgrade.js 的独立定义如何处理 | 删除，引用 core/ | 消除重复，统一数据源 |
