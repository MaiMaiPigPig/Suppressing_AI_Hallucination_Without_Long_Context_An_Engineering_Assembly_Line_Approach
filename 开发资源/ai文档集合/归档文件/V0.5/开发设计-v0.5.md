## 一、设计总览

### 1.1 排期依赖

```
v0.5-001（改名+去重） → v0.5-002（删除废弃逻辑与残件）
       ↓
    v0.6（仓库拆分）
```

v0.5-001 是 v0.5-002 的前置：v0.5-001 改完文件路径和函数名后，v0.5-002 才能在正确的文件上做删除清理。

### 1.2 执行分 5 阶段

| 阶段 | 内容 | 原因 |
|:--:|------|------|
| **P1** | 文件重命名（编号 + `package.js` 拆分） | 先稳定文件路径，后续阶段的 import 路径才正确 |
| **P2** | 函数去重（`translateDamageType`、`translateProperties`、`calcMod`） | 删副本后再改名，减少 diff 噪音 |
| **P3** | 函数改名（`calcMod`、`abilityState`、`getClassFeatures` 等） | 主体改名工作 |
| **P4** | 概念统一（`feature` 替 `trait`） | 改动量小，放最后 |
| **P5** | v0.5-002：删除废弃逻辑与残件（`ability.js` + `collectPendingSelections`/`processPendingSelections`） | 依赖 P1-P4 确认路径与引用，随清理一并处理 |

### 1.3 不改范围（已在需求中排除）

- `upgrade/`（v0.9 独立处理）
- `handlers/` 的 `parse()` 函数名（14 个子模块统一出口）
- `handlers/` 被 creation/ 直接 import 的函数名（下一节清单）
- `code-handlers/`（不在 scope）
- `dlc.js`（DLC 管理步骤，不在 17 步编号流中，仅被 `lifecycle.js` 引用，保持原名）
- 后端 API、数据文件、首页/许愿池等
