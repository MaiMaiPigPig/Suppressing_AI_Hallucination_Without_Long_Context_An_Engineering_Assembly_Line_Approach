> **关联**：本缺陷是 缺陷-v0.3-001 中 缺陷-003（范围解析结果无 table 字段）的延伸。缺陷-003 指出 `selection.js` 不产出 `table` 字段——本缺陷进一步揭示：即使修复了 `table` 字段，`proficiency(id=443→460)` 这个新数据格式也不会被路由到能正确处理它的处理器。

---

## 缺陷描述

任务卡 v0.3-001 要求的 chain 新格式是 `proficiency(id=443→460)`。当这个格式进入 `index.js` 的 `parseRule` 时：

1. 它**不会**被路由到 `proficiency.js`（因为 proficiency 路由检查 `startsWith('proficiency>')`，而新格式是 `proficiency(`）
2. 它**会被**路由到 `selection.js`（因为包含 `→` 字符，匹配 step 7 的 selection 路由）
3. `selection.js` 能解析出 `startId=443, endId=460`，但结果**不含 `table` 字段**
4. 下游代码拿到结果后无法知道应该查询 `proficiency` 表

---

## 证据

### 证据 1：proficiency 路由条件不匹配

[index.js](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/index.js) step 5：
```javascript
// Step 5: proficiency
if (rRoute.startsWith('proficiency>')) {
    return handlers.proficiency ? handlers.proficiency.parse(rule) : null;
}
```

`proficiency(id=443→460)` 以 `proficiency(` 开头，不满足 `startsWith('proficiency>')`，不进入此分支。

### 证据 2：selection 路由条件匹配

[index.js](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/index.js) step 7：
```javascript
// Step 7: selection
if (rRoute.match(/\[\d+\]/) || rRoute.indexOf('→') >= 0) {
    return handlers.selection ? handlers.selection.parse(rule) : null;
}
```

`proficiency(id=443→460)` 包含 `→`，命中此分支，进入 `selection.parse()`。

### 证据 3：selection.js range 解析结果无 table 字段

[selection.js L139-L149](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/selection.js#L139-L149)：
```javascript
var rangeMatch = rule.match(
    /(?:growup\s*\(\s*)?(\d+)\s*→\s*(\d+)(?:\s*\))?/
);

if (rangeMatch) {
    return {
        type: 'selection',
        subtype: 'range',
        success: true,
        needUserSelect: true,
        startId: startId,
        endId: endId,
        // ← 没有 table 字段！
        expression: rule
    };
}
```

注意：正则中 `(?:growup\s*\(\s*)?` 可以跳过 `proficiency(id=`，直接匹配内部的 `443→460`，所以 `startId` 和 `endId` 能正确提取——但 `proficiency` 这个表名信息被**丢弃**了。

### 证据 4：从源头到终点的完整路由追踪

```
输入: "proficiency(id=443→460)"
  ↓ handlers.parseRule()
  ↓ 预处理: 无变换
  ↓ Step 1-4: 不匹配
  ↓ Step 5 (proficiency): "proficiency(" 不以 "proficiency>" 开头 → 跳过
  ↓ Step 6 (chain): 需包含 "chain(" → 跳过
  ↓ Step 7 (selection): 包含 "→" → ✅ 命中！
  ↓ → handlers.selection.parse("proficiency(id=443→460)")
    ↓ 正则匹配: 443→460 → startId=443, endId=460
    ↓ 返回: { type: 'selection', subtype: 'range', startId: 443, endId: 460 }
    ↓ 结果: 有 ID 范围，无 table 字段，无 proficiency 上下文
```

## 影响范围

1. **当前实际数据仍是旧格式 `growup（283→302）`**，此路由缺陷尚未在生产中触发
2. **一旦数据被修正为 `proficiency(id=443→460)`**（缺陷-v0.3-004），此路由缺陷将立即暴露
3. 即使 `selection.js` 后续补充了 `table` 字段，仍需要能正确提取 `proficiency` 表名——当前正则不具备这个能力

---

## 建议

**此缺陷与缺陷-v0.3-004（数据修正）必须一起处理**，否则先修数据会导致功能彻底不工作。

**方案 A（推荐）**：在 `index.js` 中增加 `proficiency(id=...→...)` 格式的专门路由，在处理 selection 之前拦截：

```javascript
// 在 Step 5 (proficiency) 和 Step 7 (selection) 之间插入
// Step 6b: proficiency 范围引用 — proficiency(id=443→460)
if (/^proficiency\s*\(.*→/.test(rRoute)) {
    // 提取 table 名和范围，构造正确结果
    // 或者委托给专门的处理逻辑
}
```

**方案 B**：修改 `selection.js` 的 range 解析，使其能从 `proficiency(id=443→460)` 中提取表名并产出 `table` 字段：

```javascript
var tableMatch = rule.match(/^(\w+)\s*\(/);
var table = tableMatch ? tableMatch[1] : null;
return {
    // ...
    table: table,  // "proficiency"
    startId: startId,
    endId: endId,
};
```

无论选哪个方案，都需要验证：修复后的解析结果能否被下游代码（`feature-selection.js`、`review.js`）正确消费。

## 审查意见（2026-09-27）

### ❌ 核心前提错误 — 建议关闭此缺陷单

缺陷的分析链条（step 1→2→3→4→5→6→7）建立在一个错误假设上：**chain 字段的值会经过 `parseRule` 路由**。

但实际代码路径并非如此。`index.js` 的 `processItemRules` 函数[注释写明](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/index.js#L412-L414)：

> chain/choice/skills/feat 等字段包含的是数值ID或链引用，由 processChainReferences 独立处理，不在此处解析

chain 的消费者是 `review.js` 中的 `processChainReferences`，它用 `parseInt` + `split(',')` 解析 chain 值，**根本不经过 `parseRule` 路由**。因此：

- 证据 1 的 proficiency 路由不匹配 → 无关，chain 不走这条路
- 证据 2 的 selection 路由匹配 → 无关，chain 不走这条路
- 证据 4 的完整路由追踪 → 前提就错了，追踪无意义

缺陷分析逻辑自洽，但和实际代码路径无关。**建议关闭此缺陷单。**
