# 缺陷单 缺陷-v0.3-010: `proficiency(id=...)` 格式的 chain 和 rules 走两套完全不同的解析路径

| 字段 | 内容 |
|---|---|
| 编号 | 缺陷-v0.3-010 |
| 标题 | review.js 为 chain 字段手写正则解析 `proficiency(id=...)`，绕过 parseRule，与 rules 字段的解析路径不统一 |
| 关联任务 | 任务卡-v0.3-001 |
| 关联缺陷 | 缺陷-v0.3-006、缺陷-v0.3-008 |
| 审查阶段 | 测试执行 → 缺陷修复验证 |
| 提出时间 | 2026-09-27 |
| 状态 | ⛔ 已驳回（架构层面，当前 proficiency(id=...) 仅出现在 chain 字段，无 rules 路径冲突，无功能影响） |

---

## 一句话

`proficiency(id=443→460)` 这个格式在 `chain` 字段里能被 review.js 手写正则正确解析，但在 `rules` 字段里被 index.js 的 parseRule 路由到 selection.js（缺陷-006，仍未修复）。**同一个格式在两个上下文中行为不同**——不是"这个格式该怎么处理"的统一设计，而是"哪儿炸了就在哪儿打补丁"。

---

## 证据

### 证据 1：chain 的解析路径 — 手写正则，绕过 parseRule

[review.js L371-L378](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/steps/review.js#L371-L378)：

```javascript
// chain 字段不经过 index.js parseRule，直接在这手写正则：
const rangeMatch = chainStr.match(/(\w+)\(id=(\d+)→(\d+)\)/);
if (rangeMatch) {
    const startId = parseInt(rangeMatch[2], 10);
    const endId = parseInt(rangeMatch[3], 10);
    for (let id = startId; id <= endId; id++) {
        chainIds.push(id);
    }
}
```

### 证据 2：rules 的解析路径 — 如果有人在 rules 里写了 `proficiency(id=...)`，会炸

[index.js L192](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/index.js#L192)：

```javascript
// parseRule 处理 rules 字段时的路由逻辑：
// 第5步: proficiency>   → proficiency.js  ← 只匹配 proficiency> 前缀
// 第7步: 包含 →        → selection.js    ← proficiency(id=443→460) 被此步拦截！
```

`proficiency(id=443→460)` 不是以 `proficiency>` 开头，但包含 `→`，所以被路由到 selection.js。

### 证据 3：两条路径的对比

| 上下文 | 入口 | 解析方式 | 对 `proficiency(id=443→460)` 的行为 |
|--------|------|----------|--------------------------------------|
| chain 字段 | review.js `processChainReferences` | 手写正则 `(\w+)\(id=(\d+)→(\d+)\)` | ✅ 展开为 443~460 |
| rules 字段 | index.js `parseRule` → handler 路由 | 前缀/包含匹配 + 委托 handler | ❌ 路由到 selection.js，当作多选处理 |

两条路径没有任何共享逻辑。如果将来有人想在 `rules` 字段里支持 `proficiency(id=443→460)`，要么在 index.js 里重新实现一遍相同的范围解析，要么把 review.js 的正则复制到 selection.js——**不会有人想到这两处应该复用的**。

---

## 为什么会这样

不是开发的技术能力问题，是**解析流程的架构没有统一的"表达式 → 动作"转换层**。

正常的做法：
```
表达式字符串 parseRule(expr)
  ↓ 统一路由表
proficiency(...) → proficiencyHandler
spell(...)       → spellHandler
...
```

当前的做法：
```
rules 字段: 表达式 → parseRule → handler 路由
chain 字段: 表达式 → 手写正则 → 就地展开  ← 完全独立的第二条路径
```

chain 字段的格式与 rules 字段的格式完全同构（都是 `表名(id=参数)`），但没有复用 `parseRule`，而是独立手写了一套解析器。这两个解析器的行为会逐渐发散。

---

## 影响范围

| 影响 | 详情 |
|------|------|
| **当前运行时** | 低 — `proficiency(id=...)` 目前只在 chain 字段里出现，chain 不走 parseRule |
| **可维护性** | High — 将来任何人在 rules 字段里遇到 `proficiency(id=...)`，必须从零开始实现一次范围解析 |
| **一致性** | 同一种格式，两个入口，两套代码，行为可能分叉 |

---

## 建议

两种改法选一：

**A. 统一到 parseRule（推荐）**：chain 字段也走 `parseRule` → 由 handler 统一处理，review.js 里的手写正则删掉。这就要求 parseRule 能正确路由 `proficiency(id=...)`（先修缺陷-006）。

**B. 分离封装**：即使不改 parseRule，至少把范围表达式解析逻辑抽成公共函数 `parseRangeExpression(str)`，review.js 和将来 rules 的需求都调这个函数，而不是在 review.js 里就地写正则。

当前补丁式修复在当前数据下能跑，但如果 v0.4 或之后有人在 rules 里写了 `proficiency(id=...)`，就又炸了。
