## 意见-001: parseProficiencyLinkIds 存在不可达的 catch 分支

| 字段 | 内容 |
|---|---|
| 级别 | **建议** |
| 文件 | [data-query.js L284-L302](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/data-query.js#L284-L302) |
| 关联缺陷 | 无 |

### 描述

`parseProficiencyLinkIds` 的 catch 块包含逗号分隔字符串的解析逻辑：

```javascript
} catch(e) {
    refIds = raw.split(',').map(function(s) { 
        return parseInt(s.trim(), 10); 
    }).filter(function(n) { return !isNaN(n); });
}
```

此分支对应 `proficiency_link` 为逗号分隔字符串（如 `"6,11,14"`）的场景。但实际数据中，所有 `proficiency_link` 值都是 JSON 数组字符串（如 `"[6, 11]"`）或空字符串，逗号分隔格式的数据不存在。

### 验证

```bash
# 搜索所有 proficiency_link 值，全部为 JSON 数组格式
grep -rn '"proficiency_link"' TableChronicle/data/json/ | head -20
```

所有值均为 `"[...]"` JSON 数组格式。

### 建议

如果确认逗号分隔格式永不使用，可以考虑删除 catch 分支以减少维护负担。如果保留，可以加注释说明这是保留的兼容格式。

## 意见-002: review.js 调用 getCountFromProficiencyRef 缺少 level 参数，与 upgrade 流程不一致

| 字段 | 内容 |
|---|---|
| 级别 | **建议** |
| 文件 | [review.js L537](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/steps/review.js#L537) |
| 关联缺陷 | 无 |

### 描述

`review.js` 的 `collectClassExtraSelections` 中调用：

```javascript
var count = getCountFromProficiencyRef(sourceFeature, cls);
// 只传了 2 个参数，缺 level
```

对比 upgrade 流程中同一函数的调用方式：

```javascript
// upgrade.js L1129 — 3 个参数
var count = getCountFromProficiencyRef(sourceFeature, cls, level);

// level-select.js L565 — 3 个参数  
var count = getCountFromProficiencyRef(sourceFeature, cls, level);
```

`getCountFromProficiencyRef` 内部 fallback（[data-query.js L332](file:///f:/跑团工具/TableChronicle/character/dnd_5r/handlers/data-query.js#L332)）：
```javascript
var lvl = level || (typeof character !== 'undefined' && character ? 
    (character.level || 1) : 1);
```

### 分析

该场景下 `character.level` 可用（review.js 中其他位置正常使用），fallback 能正确工作，不会产生功能错误。但**调用约定不一致**，长期维护中容易造成困惑——某人可能看了 upgrade 的写法后复制到 review 时漏掉 level，反之亦然。

### 建议

统一为 3 参数调用，显式传入 level，与 upgrade 流程保持一致。
