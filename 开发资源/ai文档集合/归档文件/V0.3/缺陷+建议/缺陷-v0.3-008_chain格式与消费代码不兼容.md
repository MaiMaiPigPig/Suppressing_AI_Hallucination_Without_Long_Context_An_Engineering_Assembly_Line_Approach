## 缺陷描述

`class_features.json` 中奥法骑士和诡术师"施法"特性的 `chain` 字段值为范围表达式格式：

```json
"chain": "growup（283→302）"   // 奥法骑士
"chain": "growup（303→322）"   // 诡术师
```

但 `processChainReferences`（负责消费 chain 字段的代码）要求 chain 值是**逗号分隔的纯数字 ID 列表**。范围表达式 `"growup（283→302）"` 进入处理流程后被 `parseInt` 转为 `NaN`，被静默过滤掉。**该 chain 字段在当前代码中永远不会产生任何效果。**

---

## 证据

### 证据 1：chain 消费者只认逗号分隔数字

[review.js L363-L370](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/steps/review.js#L363-L370)：
```javascript
if (source.chain) {
    const chainStr = String(source.chain);
    const chainIds = chainStr.split(',')
        .map(id => parseInt(id.trim()))
        .filter(id => !isNaN(id));
    // 对于 chainStr = "growup（283→302）"：
    //   split(',') → ["growup（283→302）"]
    //   parseInt("growup（283→302）") → NaN
    //   filter → [] ← 空数组！循环体不执行
    for (const targetId of chainIds) {
        const target = findInAllTables(targetId);
        if (target) {
            await collectSelectionsFromSource(target, visited);
        }
    }
}
```

### 证据 2：全代码库仅此一处 chain 消费者

`processChainReferences` 是唯一处理 `chain` 字段的代码。升级系统（`upgrade.js`）对 chain 的使用仅限于 `class_extra` 的纯数字 chain（如 `"4,5"`），不处理范围表达式。

### 证据 3：法术系统完全绕过 chain

法术位/戏法/准备法术的数据获取全部通过 `getSpellDataFromProficiency(classId, level)` 直接查询 `proficiency.json`，不经过 chain：

| 模块 | 数据获取方式 | 是否经过 chain |
|------|------------|:---:|
| [spells.js L83](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/steps/spells.js#L83) `getSpellDataFromProficiency` | `dataCache.proficiency` 按 class_id+level 直查 | ❌ |
| [spell-update.js](file:///f:/跑团工具/TableChronicle/character/dnd_5r/upgrade/steps/spell-update.js) | 调同一函数 | ❌ |
| [character.js L692](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/character.js#L692) | 调同一函数 | ❌ |

### 证据 4：CSV 数据源格式

[环位熟练.csv](file:///f:/跑团工具/开发资源/data/csv导出/环位熟练.csv) 中奥法骑士的 18 条数据（443-460）和诡术师的 38 条数据（461-498）各自独立成行，字段包括 `type`（cantrip/spell_preparation/spell_slots）、`value`、`slot_1`~`slot_9` 等。

要把这些数据通过 chain 引用，需要的格式是 18 个或 38 个逗号分隔的数字 ID，而不是一个范围表达式。

## 输入输出追踪

```
输入: class_features.json id=261, chain="growup（283→302）"
  ↓ review.js · collectSelectionsFromSource()
  ↓ addPendingSelectionsFromItem(source) — 扫描 rules/tool 等字段（不扫描 chain）
  ↓ processChainReferences(source):
    ↓ chainStr = "growup（283→302）"
    ↓ split(',') → ["growup（283→302）"]
    ↓ parseInt("growup（283→302）") → NaN
    ↓ filter → []
    ↓ for 循环不执行
  ↓ 结果: chain 被静默丢弃，无任何效果

对比: 法术系统
  ↓ spells.js · getSpellDataFromProficiency(5, level)
  ↓ dataCache.proficiency 中查 class_id=5 的所有条目
  ↓ 按 level 筛选取最大值
  ↓ 结果: 正确返回奥法骑士的法术数据（独立于 chain）
```

## 影响范围

| 影响 | 详情 |
|------|------|
| **当前运行时** | 无影响 — 法术系统走独立路径，chain 不起作用 |
| **chain 修正后** | 即使把 chain 改成 `proficiency(id=443→460)`，`processChainReferences` 仍然不处理 — `parseInt("proficiency(id=443→460)")` → `NaN` |
| **正确生效的前提** | 要么改成 18/38 个逗号分隔数字（不现实），要么 `processChainReferences` 需要支持范围表达式 |

---

## 建议

这是一个设计层面的缺陷——数据格式与代码逻辑不匹配。需要从两个层面中选择一个来解决：

**层面 A：数据格式适配代码** — 将 chain 改为代码能解析的格式（逗号分隔数字）。但这需要 18 或 38 个 ID 写入一条 chain，不现实。

**层面 B：代码支持新格式** — 扩展 `processChainReferences` 使其能解析范围表达式，或新增独立的范围处理逻辑。这与缺陷-v0.3-006（路由缺陷）和缺陷-v0.3-001 的缺陷-003（消费代码缺失）是**同一链条**。

**当前实际结论**：由于法术系统走了独立路径（`getSpellDataFromProficiency`），chain 即使不修正也不影响奥法骑士/诡术师的施法功能。但 chain 字段本身持有错误数据 + 错误格式，属于**数据债**，应修正以防将来有新代码依赖它。
