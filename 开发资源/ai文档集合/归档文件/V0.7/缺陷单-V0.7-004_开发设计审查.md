## 缺陷 1：步骤 A/B/C 引用的 `13-review.js` 在步骤 D 才被创建，中间态断裂

**严重程度**：🔴 阻塞
**状态**：✅ 已解决（2026-10-03 设计已更新采纳）

### 问题描述

设计 2.2 给定了严格操作顺序：

```
A: 迁移 09-feature-selection 子文件到 13-review-*
B: 更新 review 内部 import
C: 更新外部 import（step-router/navigation/lifecycle/app.js）
D: 步骤文件批量重命名（10→9, 11→10, ... 17→16）  ← 13-review.js 在此步创建
```

但 A/B/C 三步中多处引用了 `13-review.js`，而该文件要到步骤 D 重命名 `14-review.js` 时才被创建。

| 步骤 | 文件 | 设计中的 import | 实际存在？ |
|:--:|------|------|:--:|
| A | `13-review-engine.js`（新建） | `from './13-review.js'` | ❌ 不存在 |
| B | `14-review-main.js` | `from './13-review.js'` | ❌ 不存在 |
| B | `14-review-collector.js` | `from './13-review.js'` | ❌ 不存在 |
| C | `navigation.js` | `from '../steps/13-review.js'` | ❌ 不存在 |
| C | `lifecycle.js` | `from '../steps/13-review.js'` | ❌ 不存在 |
| C | `app.js` | `from './steps/13-review.js'` | ❌ 不存在 |

**证据**：

- [14-review.js](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/steps/14-review.js) 是当前唯一对外入口，`13-review.js` 不存在于当前代码库中

- 步骤 D 的操作表中明确列出 `14-review.js → 13-review.js` 的重命名，证实 `13-review.js` 在该步才被创建

### 正确的顺序

步骤 A/B/C 中所有指向 `13-review.js` 的 import 应先指向 `14-review.js`（该文件在步骤 2.4.1 已追加 re-export，可承担统一入口角色），步骤 D 重命名 `14-review.js → 13-review.js` 后，再全局替换 `14-review` → `13-review`。

### 建议

在 2.2 操作顺序中新增一步 D.5：**重命名完成后，全量替换 `from.*14-review` → `from.*13-review`**，并明确步骤 A/B/C 中的 import 目标先用 `14-review.js`（加注释标记待 D.5 更新）。

### 处理结果

设计 2.2 操作顺序已新增 D.5 步骤并补充关键约定：**步骤 A/B/C 中所有跨文件 import 暂用 `14-review.js`，待 D 完成重命名后在 D.5 统一替换为 `13-review.js`**。逐项核实：

## 缺陷 2：navigation.js 步骤号比较 L55 映射错误

**严重程度**：🔴 阻塞
**状态**：✅ 已解决（2026-10-03 设计已更新采纳）

### 问题描述

设计 2.10.2 列出 navigation.js 的步骤号比较变更：

| 行号 | 原值 | 改为 | 上下文 |
|:--:|:--:|:--:|------|
| 55 | `=== 12` | `=== 10` | 专长已选检查（原 12→11→10）|

但验证 [navigation.js:55](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/flow/navigation.js#L55) 实际代码：

```javascript
if (currentStep === 12 && !character.selectedFeat) {
    alert('请确认专长');
    return;
}
```

当前步骤映射（重编号前）：

| 步骤 | 内容 |
|:--:|------|
| 10 | 技能 |
| 11 | 专长 |
| 12 | 法术 |

`=== 12` 当前在**法术步骤**检查"请确认专长"——即到了步骤 12（法术）时，验证用户已在步骤 11（专长）完成了选择。重编号后：

| 步骤 | 内容 |
|:--:|------|
| 9 | 技能 |
| 10 | 专长 |
| 11 | 法术 |

重编号后法术是步骤 11，等价检查应为 `=== 11`。

设计给出的 `=== 10` 会使检查发生在**专长步骤本身**（而不是专长之后），此时用户还没选专长，检查必然触发 alert 阻止前进，形成死循环。

**正确的映射**：`=== 12` → `=== 11`

（注：注释中"原 12→11→10"暗示中间经过两轮编号变化，但本次重编号只做一轮：12→11，不跳 10。）

### 建议

L55 改为 `=== 11`，同时检查 2.10.2 表中其他条目是否因同一推算链存在偏移。

### 处理结果

设计 2.10.2 已改为 `=== 12` → `=== 11`，注释补全推导链："当前：步骤 12=法术时，检查步骤 11=专长已选；顺延后：步骤 11=法术时，检查步骤 10=专长已选"。其余 6 项（L59/66/87/119/177/179）经逐项核实均正确。

## 缺陷 5：Stage 3 正则替换会丢失 `tool=N` 格式兼容（2026-10-03 复查新增）

**严重程度**：🔴 阻塞
**状态**：✅ 已解决（2026-10-03 设计已更新采纳）

### 问题描述

设计 4.2.2 将匹配 `tool=4` 格式的正则直接替换为 `tools?(id=N)+M` 格式：

```diff
- 旧正则：/^tool\s*=\s*(\d+)$/i          → 匹配 tool=20
+ 新正则：/^tools?\s*\(\s*id\s*=\s*(\d+)\s*\)\s*(?:\+(\d+))?$/i → 匹配 tools(id=20)+1
```

但 `tool=N` 格式在生产数据中仍然存在：

**证据**：[套装详情.csv:44](file:///f:/跑团工具/开发资源/data/csv导出/套装详情.csv#L44)：
```
43,tool=20,1,赌具（任意）
```

设计声称"兼容 tools(id=N)+N"，但实际**替换了**旧格式，而非追加新分支。新正则可以匹配 `tools(id=20)+1`，但 `tool=20` 无法匹配任何分支，会落到 else → 显示原始字符串 `tool=20` → 工具名解析失败。

**波及范围**：同时影响 `05-background.js:91` 和 [08-bonus.js:295](file:///f:/跑团工具/TableChronicle/character/dnd_5r/creation/steps/08-bonus.js#L295)（同一正则）。

### 建议

两种格式差异太大（`tool=N` vs `tools(id=N)+M`），不适合合并为一个正则。保留旧分支，新增第三分支：

```javascript
// 格式3（新增）：tools(id=N)+M
const toolIdExplicit = toolStr.match(/^tools?\s*\(\s*id\s*=\s*(\d+)\s*\)\s*(?:\+(\d+))?\s*$/i);
if (toolIdExplicit) {
    const toolId = parseInt(toolIdExplicit[1]);
    const count = toolIdExplicit[2] ? parseInt(toolIdExplicit[2]) : 1;
    // 同 tool=N 逻辑
}
// 格式2（保留）：tool=N（向后兼容）
else {
    const toolIdMatch = toolStr.match(/^tool\s*=\s*(\d+)$/i);
    if (toolIdMatch) {
        const toolId = parseInt(toolIdMatch[1]);
        const t = (dataCache.tools || []).find(tl => tl.id === toolId);
        toolName = t ? t.name : (toolIdMatch[1] + '号工具');
    }
    else {
        toolName = toolStr;
    }
}
```

### 处理结果

设计 4.2.2 完全重写：标题从「扩展正则」改为「追加 tools(id=N)+N 分支（**非替换**）」；明确旧分支「**保留不动**」；新增第三分支匹配 `tools(id=N)+N`；引用 `套装详情.csv L44 tool=20` 为数据证据；4.2.4 同步标注「两处均需在现有分支下方追加，不替换」。不再存在格式丢失风险。

## 缺陷 6：Stage 7 设计与测试脚本现有实现结构冲突（2026-10-03 复查新增）

**严重程度**：🟠 中等
**状态**：✅ 已解决（2026-10-03 设计已更新采纳）

### 问题描述

测试脚本[已实现](file:///f:/跑团工具/测试脚本/车卡_回归测试.py)了浏览器 console 捕获功能：

| 已有方法 | 行号 | 功能 |
|------|:--:|------|
| `_capture_console(step_label)` | L295 | 拉取 browser log（SEVERE + WARNING） |
| `get_console_summary()` | L331 | 按步骤分组的结构化汇总 |
| `print_console_summary()` | L353 | 终端打印可读汇总报告 |

设计 8.1 提议新增：

| 设计方法 | 功能 |
|------|------|
| `collect_console_errors()` | 仅 SEVERE 级别 |
| `print_step_console_summary(step_num)` | 每步即时打印 |

两者功能重叠（都做 console 收集和打印），但方法名和结构不一致。`goog:loggingPrefs` 能力已在 `__init__` 中设置（L1909），`go_next` 末尾已调用 `_capture_console`（L427），`run_full_flow` 末尾已调用 `print_console_summary`（L1859）。

如果开发按设计新增方法，会出现功能重复的冗余代码，或命名冲突。设计应标注现有实现状态，避免重复。

### 建议

设计 8.1 改为标注"测试脚本已有 console 捕获实现（`_capture_console`/`print_console_summary`），以下描述仅供参考，与现有实现对齐即可"，避免开发重复造轮子。

### 处理结果

阶段 7 完全重写：新增「现状说明」块，列出已有 3 个方法及其行号（`_capture_console` L295、`get_console_summary` L331、`print_console_summary` L353）；明确「**不要重复实现相同功能**」；原有新增方法 diff 改为「现有实现对齐检查清单」（标注各方法是否已满足需求）。不再存在开发重复实现的隐患。
