## 六、风险与应对
| 风险 | 应对 |
|------|------|
| Python/JS 正则行为差异导致解析不一致 | 两端使用相同正则模式，转换后抽检 JSON 和前端渲染结果 |
| `spell-level.js` 的 `extractLinkId()` 改为表达式解析后，class/school 提取逻辑出错 | 单独测试法术等级相关的 code handler，确保从 `spells(class=12,school=7)+2` 正确提取参数 |
| 引用表中 type=rule/rules 在前端无对应处理分支 | 确认这些条目实际处理路径（basic.js 直接匹配），迁移后无需额外改动 |
| 自描述表达式长度增加导致 CSV 可读性下降 | 使用 Excel/LibreOffice 的自动换行功能，不影响程序解析 |
| 6 个 CSV 已手动替换，开发重跑脚本时可能覆盖 | 开发使用已生成的 `link_mapping.csv`，不要重新跑 replace_links.py |

## 七、测试建议
- **重点测**：
  - 车卡流程中所有涉及选项选择的步骤（种族法术、职业特性、专长选择、背景熟练）
  - `spells(class=X,lv=Y)+N` 格式的法术筛选是否正确渲染
  - `choose(...)` 和 `[1]...[2]...` 多选一格式是否正确
  - `prerequisite(...)` 先决条件是否正确显示和校验
- **容易漏的**：
  - `spell-level.js` 从 rules 字段提取参数的边界情况
  - `proficiency>pure+2` 这类无表名前缀的裸表达式
  - `chain:54` 和 `code(choose)` 等非 link 语法是否被误改动
  - 升级模块 `upgrade.js` 中的 `proficiency_link` 是否间接依赖引用表
