# 方案评估 开发-003

## 一、需求理解
将现有 `link(id)` 魔法数字引用全面替换为自描述表达式（如 `feats(id=5)`、`spells(class=3,lv=0)+2`），废除引用表中间层，使规则数据人类可读、AI 可直接生成。

## 二、能不能做
- 结论：**能做**
- 理由：迁移指南提供了 `convert_link` 函数能自动转换 340 条引用表的 7 种 type（id/filter/choose/type/special/spell_slot/prerequisite/rules），覆盖率足够。前端正则解析器已在规范中设计好，向后兼容策略有方案。

## 四、怎么改

**分两阶段推进，不搞大爆炸式替换。**

**阶段一（脚本侧）：**
1. 跑 `migrate_link.py` 脚本，读取引用表 340 条，逐一调用 `convert_link` 生成新表达式映射
2. 跑 `replace_links.py` 批量替换 6 个 CSV 文件中的所有 `link(id)`
3. 在 `csv转json.py` 中加入 `ExpressionParser`（迁移指南已提供骨架代码），让 JSON 输出同时包含新旧两种格式（过渡用）

**阶段二（前端侧）：**
1. `handlers/link.js` 改为优先级策略：输入先尝试新表达式正则匹配，匹配不上再走旧 `link()` 查引用表
2. `handlers/index.js` 中 `parseRule` 增加新表达式分支（`feats(`, `spells(`, `choose(` 等前缀判断）
3. 各 step 文件中的 link 硬编码（先决条件展示、法术规则解析等）逐步改为直接消费新表达式

## 五、风险
- **风险1：正则差异。** Python 和 JavaScript 的正则引擎行为不完全一致。规范的 regex 已在 JS 端给出，但未在 Python 端验证。迁移后 CSV→JSON 的解析链路可能出现两边行为偏差，需在转 JSON 后抽检。
- **风险2：JSON 数据体积膨胀。** `link(257)` 是 10 字节，`spells(class=3,lv=0)+2` 是 23 字节。引用表 779 处出现（JSON 侧），全替换后 JSON 总体积会增大。虽不致命但需要关注。
- **风险3：前端代码散布。** link 解析逻辑散落在 handlers/link.js、index.js、spells.js、review.js、feature-selection.js、feat.js、background.js、spell-level.js 共 8 个文件中，每处都可能需要调整，容易出现遗漏。
- **风险4：数量运算符 `+N` 的新旧同名冲突。** 旧表达式 `proficiency>pure+2` 中的 `+2` 与新表达式 `tools(type=66)+3` 中的 `+3` 在正则中需要正确区分，解析器设计不当会导致歧义。

## 六、依赖
- 依赖 `10_自描述表达式规范.md` 中的 10 种表达式类型全部确定（目前有 4 种无旧引用表对应：范围选择、多选一、属性/数值运算、代码标记——但这些在 CSV 中可能不通过 link 出现，而是直接内联）
- 依赖 `11_引用表迁移指南.md` 中的 `convert_link` 函数对所有 340 条引用表条目能正确处理（目前覆盖 7 种 type，需验证无遗漏的 type 值）

## 七、不确定项
- **需确认：** `chain:` 和 `code()` 在 CSV 中是直接写在字段里的，不走 `link()` 引用表，这部分本身就已经是自描述的，迁移脚本需要跳过它们而不是误替换。
- **需确认：** `[1]link(103),[2]link(257)` 这种带选项标记的多选一格式，迁移后变成 `[1]feats(type=44)+1,[2]spells(class=3,lv=0)+2`。前端是否正确处理选项标记与自描述表达式的嵌套？
- **需确认：** 引用表中 `type=rules` 的条目（如 `hp_per_lv+2`），转换后直接输出裸表达式不带表名。前端能否正确处理不带表名前缀的裸表达式？
- **需确认：** 规范文档中的表名对照有 `背包/物品 → items`，但实际 CSV 文件名是 `背包.csv`，csv转json.py 中映射为 `items`。而规范中还有 4 个表（conditions/combat_actions/scenes/encounters）在 csv转json.py 和现有数据中完全不存在，是远期规划还是规范超纲？

## 八、代价
- 工作量：**中**（6 个 CSV 共 325 处替换 + 1 个 Python 脚本改造 + 8 个 JS 文件适配）
- 复杂度：**中**（需要同时维护两套解析逻辑直到切换完成，正则兼容性需要两端验证）
- 维护成本：**低**（迁完后删除引用表 CSV，后续新增数据直接用自描述表达式，不再需要分配 link id）

## 九、替代方案
- **方案A（推荐）：分阶段渐进迁移。** 先在 `link.js` 中增加解析缓存层——解析 `link(id)` 后缓存为自描述表达式，后续前端消费缓存的表达式。这样现有的 `link(id)` 继续工作，但内部已切换到新表达式。完全稳定后，再批量替换 CSV 和 JSON 源数据。代价：多了缓存层的复杂度，但风险更低，可随时回退。
- **方案B：纯替换。** 一次性跑脚本替换所有 CSV + 重跑 csv转json.py + 改前端，不留兼容。代价：出问题时只能回滚文件，没有灰度。

## 十、结论
**建议做，采用方案A（分阶段渐进迁移）。** 先在 JS 端实现新旧双解析 + 缓存，验证通过后再批量替换数据源。325 处 CSV 引用 + 779 处 JSON 出现 + 8 个 JS 文件改动，量级可控，但正则两端一致性是最大风险点，需先做小范围验证。
