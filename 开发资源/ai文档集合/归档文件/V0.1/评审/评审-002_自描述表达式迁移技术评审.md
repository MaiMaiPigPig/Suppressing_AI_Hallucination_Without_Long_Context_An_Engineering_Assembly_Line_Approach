# 评审单 评审-002: 自描述表达式迁移技术评审

## 1. 评审目标
- **评审对象**：`10_自描述表达式规范.md` 定义的 10 种表达式类型，以及 `11_引用表迁移指南.md` 的 `convert_link` 函数实现
- **评审重点**：每种表达式类型能否从旧 `link(id)` 自动迁移，表名映射是否一致

## 2. 评审清单

### 2.1 表达式类型迁移可行性

| 序号 | 表达式类型 | 规范示例 | 旧引用表是否有对应 type | 结果 | 备注 |
|---|---|---|---|---|---|
| 1 | 基本引用 | `feats(id=5)` | ✅ type=id | ✅ 可自动迁移 | csv转json.py 透传，引用表 type=id 占 ~250 条主体 |
| 2 | 多条件筛选 | `spells(class=3,lv=0)+2` | ✅ type=filter | ✅ 可自动迁移 | link.js 中 type=filter 分支已验证：拼 `filterTableName(complex_logic)+count` |
| 3 | 手动列表选择 | `choose(skills(21,22))+1` | ✅ type=choose | ✅ 可自动迁移 | link.js 中 type=choose 分支：拆 complex_logic 为 ID 数组 |
| 4 | 范围选择 | `growup(303→322)` | ❓ 需确认 | ⚠️ 需确认 | 引用表中 growup 表条目使用 type=id，target_id 逐个列出，没有 id→id 范围语义。需确认规范中的 `→` 语法是否只在 growup 表内使用，以及是否需要调整引用表的数据结构 |
| 5 | 特殊操作 | `all(skills)` | ✅ type=special | ✅ 可自动迁移 | link.js 中 type=special 分支已处理 all/half-prof/proficiency>pure/choose(...)/spell-level 共 5 种子类型 |
| 6 | 多选一 | `①feats(type=44)+1,②spells(class=3,lv=0)+2` | ❌ 无对应 | ❌ 无需迁移 | 选项标记 `[1]`/`[2]`（或 `①`/`②`）在数据行的 rules 字段中直接内联，不是通过 `link()` 引用的。如 `[1]link(103),[2]link(257)`，迁移脚本只需要替换内部的 `link(id)` 为自描述表达式，外层 `[1]`/`[2]` 标记本身保持不变 |
| 7 | 属性/数值运算 | `AbilityModifiers(1)` | ❌ 无对应 | ❌ 无需迁移 | 这些表达式直接写在数据行的 rules 字段中，从来不走 `link()` 引用表。index.js 中的 parseRule 已经有对应匹配分支（L104-109, L133-140） |
| 8 | 前置条件 | `prerequisite(lv>=4)` | ✅ type=prerequisite | ✅ 可自动迁移 | 引用表 id=506~531 共 26 条，complex_logic 格式与规范中的 prerequisite() 参数格式一致 |
| 9 | 连锁引用 | `chain:54` | ❌ 无对应 | ❌ 无需迁移 | `chain:` 语法在数据行的 "连锁"（chain）列中，不走 `link()`。index.js L168-171 已有独立匹配分支 |
| 10 | 代码标记 | `code(choose)` | ❌ 无对应 | ❌ 无需迁移 | `code()` 语法在数据行的 "代码"（code）列中，不走 `link()`。index.js L381-423 已有 CodeHandlers 独立处理流程 |

**总结**：10 种表达式类型中，**4 种可直接通过引用表自动迁移**（id/filter/choose/special），**2 种需要确认但可迁移**（范围选择/prerequisite），**4 种无需迁移**（多选一/属性运算/连锁引用/代码标记——它们本来就不走 link）。

### 2.3 其他技术意见

```
【开发填写区】

1. 关于多选一(①②③)：
   无需迁移。旧数据中的多选一格式是 [1]link(103),[2]link(257)，[1]/[2] 标记本身不是 link 语法。
   迁移脚本只需替换内部的 link(id) 为自描述表达式，外层标记保持不变。
   迁移后变成 [1]feats(type=44)+1,[2]spells(class=3,lv=0)+2，前端 handlers/selection.js 已能处理。

2. 关于连锁引用(chain:54)：
   无需迁移。chain: 语法在 CSV 的 "连锁"(chain) 列中，不走 link()。
   index.js L168 有独立匹配 `if (r.startsWith('chain:'))`，已可识别。
   规范中的 chain: 语法与现有代码一致。

3. 关于代码标记(code())：
   无需迁移。code() 语法在 CSV 的 "代码"(code) 列中，不走 link()。
   前端 CodeHandlers 系统已独立处理。但有个隐患：spell-level.js 中用
   `extractLinkId()` 从同行的 rules 字段提取 link(ID)，这意味某些 code 处理器
   间接依赖 link(ID) 来查引用表。迁移时需要让这些处理器改为从自描述表达式获取参数。

4. 其他发现：
   a) 引用表中有两个容易混淆的 type 值：
      - type=rule（id=309，single entry）→ 用于"规则模式描述"，hp_per_lv+N
      - type=rules（id=514-517，4 entries）→ 用于"直接执行的裸规则表达式"
      这两个 type 在 link.js 中都没有对应的分支处理！查询 link.js 代码，只处理了
      id/filter/type/choose/special/spell_slot 共 6 种分支，没有 type=rule 或
      type=rules 的处理逻辑。这可能意味着这些条目在前端运行时不会通过 link.parse()
      被解析，而是被其他路径处理（如 basic.js 直接匹配 hp_per_lv+ 前缀）。

   b) spell-level.js 的 extractLinkId 是迁移的盲点。它用正则从 rules 字段提取
      link(ID)，然后手动查引用表获取 class/school 过滤条件。迁移后 rules 字段变成
      自描述表达式（如 spells(class=12,school=7)+2），需要改写为从表达式直接解析
      class/school 参数。

   c) link.js 中的表名单复数归一化（singularMap）是当前架构的补丁：
      lookup_table 存复数 → filter handler 只认单数 → 所以需要归一化。
      迁移到自描述表达式后，如果前端解析器统一使用复数表名，这个归一化逻辑可以移除。
      但需要确保所有 handler（filter/tableRef 等）同步升级为认复数。
```

## 3. 评审结论
- **总体结果**：可行，建议推进
- **必须修改项**：
  - `规范第3节` 补充 `class_extra`、`subclasses` 两个表名
  - `spell-level.js` 的 `extractLinkId()` 改为从自描述表达式解析参数
  - 迁移脚本需处理 `link.js` 未覆盖的 type=rule/rules 条目（确认其实际处理路径后再定方案）
- **建议修改项**：
  - 规范中 4 个远期表（conditions/combat_actions/scenes/encounters）标注为"规划中"，避免误解为当前已实现
  - 前端 handler 的表名单复数统一为复数，移除 singularMap 补丁

## 4. 风险与依赖
- **技术风险**：`spell-level.js` 通过正则 `/link\(\s*(\d+)\s*\)/` 间接依赖 link ID，迁移后这里会断链，必须同步改造。其他 code handler 也可能有类似隐式依赖需要逐一排查。
- **依赖项**：迁移脚本依赖引用表 340 条全部可转换，需先验证没有 type 值超出 convert_link 的处理范围（已确认存在 type=rule 和 type=rules 未被 link.js 覆盖）。
