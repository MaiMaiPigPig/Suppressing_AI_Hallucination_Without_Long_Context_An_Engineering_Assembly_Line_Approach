### DEF-TC-13：B-14 归类错误 + Resource 模块测试用例缺失

**严重度**：高  
**用例**：B-14 + Resource 模块  
**状态**：已修正（测试侧）

**问题定性**：`character(获得黑暗视觉)` 被错误归入 basic 模块，且整个 Resource 处理器无测试覆盖。

**源码证据**：

`index.js` 路由有两个与 `character(` 相关的分支，按先后顺序：
```js
// 第68行：优先命中，仅匹配 character(直接显示)
rRoute.includes('character(直接显示)') → basic.parse()

// 第98行：兜底，匹配所有 character(任意名称)
rRoute.startsWith('character(') → resource.parse()
```

`resource.js` 已完整实现两个子模式：
```js
// 子模式1：Character(资源名称)+数值 → subtype:'add', resourceName, value
// 子模式2：Character(资源名称)      → subtype:'reference', resourceName
```

**具体影响**：

| 层面 | 现状 | 问题 |
|------|------|------|
| 用例文档 B-14 | 归在 basic 模块，预期 `subtype:"display", success:true` | `character(获得黑暗视觉)` 不包含 `character(直接显示)`，basic.parse() 直接返回 `success:false`。实际路由走 resource |
| 用例文档 Resource | **不存在** | 映射表 §八 定义了 `Character(资源名称)` 和 `Character(资源名称)+数值` 两条规则，但没有对应测试用例 |
| 测试脚本 Resource | **不存在** | 源码 `resource.js` 存在但没有 `resource.test.js` |

**修正要求（开发侧）**：

1. **B-14**：从 basic 模块**移除**（basic.parse() 直接调用时确实返回 `success:false`，脚本没问题）
2. **新增 Resource 模块测试用例**：覆盖 `Character(名称)`、`Character(名称)+数值`、边界与非法输入
3. **新增 resource.test.js 测试脚本**：与用例对齐

**测试侧已完成**：
- B-14 预期改为 `type:"basic", success:false`，覆盖点说明实际走 resource 路由
- 新增模块 11（R-01~R-14）14 条用例
- 新增 I-14/I-15 两条 resource 路由测试
- 开发侧仍需补写 `resource.test.js` 脚本


### DEF-TC-14：I-22 路由期望错误 — `spell:140` 不被 index.js 路由到 chain

**严重度**：高  
**用例**：I-22  
**状态**：已修正（用例侧）

**问题定性**：用例预期 `parseRule("spell:140")` 路由到 `chain.cross_table`，但 index.js 路由使用 `rRoute.startsWith('chain:')`，不匹配 `表名:ID` 格式。实际落入兜底 `type:"unknown"`。

**源码证据**：

index.js 路由逻辑中，chain 路由分支：
```js
// 仅匹配 "chain:N" 格式
if (rRoute.startsWith('chain:')) {
    return chain.parse(rule);
}
```

`"spell:140"` → `rRoute = "spell:140"` → 不满足 `startsWith('chain:')` → 跳过。

逐层排查全部 20+ 个路由分支后确认：无一命中 `spell:140`。最终落入：
```js
return { type: 'unknown', success:false, ... };
```

**说明**：`chain.parse("spell:140")` 直接调用正常工作（CN-04 不受影响）。仅 `parseRule` 路由层不覆盖。

**修正**：I-22 预期改为 `type:"unknown", success:false`，覆盖点注明路由不匹配原因。

### DEF-TC-16：R-14 预期错误 — `null` 输入会被正则匹配成功

**严重度**：高  
**用例**：R-14  
**状态**：**不成立**（已撤销）

| 字段 | 内容 |
|------|------|
| 提报内容 | 输入 `null`，预期 `success:false`。声称 `String(null)`→`"null"`，正则 `character\((.+)\)` 会匹配 `"null"` |
| 核实结论 | **不成立**。源码 `resource.js` 正则 `/^character\s*\(/i` 要求字符串以 `character(` 开头，`"null"` 以 `n` 开头，不可能匹配。两正则均不命中，fallback 返回 `success:false`，用例预期正确 |
| 不改原因 | 用例预期 `success:false` 与源码行为完全一致，无需修改。提报人误把正则 `character\((.+)\)` 中的 `(.+)` 理解为"可以匹配任意字符串包含 `character(N)`"，忽略了正则开头的 `^` 锚定了必须从 `character(` 开头 |
| 备注 | 当前 R-14 实际输入为 `"some_random"` 而非 `null`，但不影响结论：两种输入都不会被 resource 正则匹配 |
