## 一、核心协作流程（严禁越权）

1. **先讨论，后动手**

   - 任何 AI 在修改代码前，必须先说明思路和方案。
   - 只有在人类明确说"动手 / 执行 / 开始改"之后，才能修改代码。
   - 禁止在讨论阶段私自改代码、提交 commit 或生成文件。
2. **最小改动原则**

   - 修复 Bug 时，只改导致问题的最小范围。
   - 严禁借机重构无关代码、调整格式、重命名变量。
   - 如需重构，必须单独作为任务卡提出，经批准后执行。
3. **诚实汇报**

   - 开发完成报告必须包含真实的运行命令和结果。
   - 有妥协、偷懒、未覆盖的边界，必须主动写明，不得隐瞒。
4. **任务汇报格式（强制）**

   面向产品人员的汇报，不是技术报告。四段式：

   - **① 哪个功能**：用户能感知的什么功能、什么页面
   - **② 干什么**：用户看到什么、得到什么效果
   - **③ 数据从哪来**：原始数据在哪（策划表/配置）、谁在改它
   - **④ 为什么动**：不改用户会遇到什么问题

   > 示例见 `任务-V0.7-001-A_dictionary.js消除window依赖.md` 前四节。

## 二、架构红线（最高优先级）

本项目采用严格的**逻辑层与展示层分离**架构：

### 公共逻辑层

- 目录：`TableChronicle\character\dnd_5r\handlers\` 和 `code-handlers\`
- 职责：所有外连接、数据映射、规则解析、索引构建等通用逻辑。
- 目标：纯规则引擎，不绑定任何 UI，可跨项目直接复用（以后开发别的 D&D 工具直接搬）。

### 展示/流程层

- 目录：`upgrade\`、`creation\` 等业务流程文件夹
- 职责：只负责页面渲染、步骤导航、UI 交互。
- **绝对禁止**：在流程层自己写一套查表、映射、解析的代码。

### 统一的数据使用模式

1. 加载数据 → 调用 handlers 层建索引（如 `buildDataIndexes`）
2. 查询 / 筛选 → 全走 handlers 层函数（如 `handlers.parseRule`、`extraByFeatureId` 等 O(1) 索引）
3. 渲染 UI → 使用 handlers 层返回的数据

### 架构自检清单（写代码前必读）

- [ ] 这段逻辑是不是 handlers 里已经有了？（先去 grep 搜索）
- [ ] 我是不是在业务流里手写了查表、映射代码？
- [ ] 如果 handlers 里没有，是不是应该加到 handlers 里复用？

## 三、AI 注释规范（大白话，说人话）

代码基本没注释，先解决"有没有"。用大白话解释这段在干嘛、为什么这么写，想象给刚入职同事讲代码。

**必须写**：文件头（三句话说清功能+数据来源）、每个 export 函数（入参举例+出参+干了什么）、正则（匹配什么、分组含义）、map/filter/reduce 链（每步变什么）。

**别写**：翻译代码动作的废话（`// 把 a 加 1`）、TODO、`// 调用某某函数`。

## 六、环境问题处理

- 插件报错（如 `no_sid.no_ppe`）属于人类运维范畴，AI 不参与排查。
- AI 不得以"环境问题"为由擅自修改代码或配置。
- 环境问题由人类自行处理，处理完毕后 AI 继续按任务卡工作。

## 七、归档隔离规则

- 开发资源\ai文档集合\当前工程--》 是当前活跃工作区，所有任务流转只在这里进行。
- 开发资源\ai文档集合\归档文件--》 是历史归档区，**AI 禁止读取、搜索、引用 文件夹 下的任何文件，除非人类有要求**。
- 如果 AI 需要了解历史决策，必须由人类明确指定具体文件路径，否则不得自行翻阅。
- 每次开工前，AI 只阅读 `active/` 下与当前任务相关的文档。

## 八、文档流转与归档规则

### 8.1 双区制

本项目文档采用**活跃区 / 归档区**双区制：

| 区域   | 路径                              | 用途                                        | AI权限               |
| ------ | --------------------------------- | ------------------------------------------- | -------------------- |
| 活跃区 | `开发资源/ai文档集合/当前工程/` | 进行中的任务、待修复的Bug、待验收的报告     | 读写                 |
| 归档区 | `开发资源/ai文档集合/归档文件/` | 已验收完成的任务、已关闭的Bug、已用完的文档 | 仅写入（人类指令后） |

### 8.2 文档生命周期

```
创建 → 流转 → 验收 → [人类确认] → 归档 → 封存
```

- **创建**：AI根据任务新建文档，放入活跃区
- **流转**：文档在任务卡/Bug单/报告之间流转，AI可读写
- **验收**：人类审阅并确认通过
- **归档**：人类明确说"归档"后，AI将文档移入归档区
- **封存**：归档区文档AI禁止读取（见第七章）

### 8.3 归档条件（必须全部满足）

**核心原则：人类验收后才能归档。AI不得自行判断验收状态。**

| 文档类型        | 归档条件                                                  |
| --------------- | --------------------------------------------------------- |
| 任务卡 (需求-*) | 开发完成 + 测试通过 +**人类明确说"验收通过，归档"** |
| Bug单 (缺陷-*)  | 修复完成 + 复测通过 +**人类明确说"关闭，归档"**     |
| 开发文档        | 开发已用完 + 功能已上线 +**人类明确说"归档"**       |
| 测试报告        | 测试完成 + Bug已闭环 +**人类明确说"归档"**          |
| 改进建议        | 建议已采纳并实施 +**人类明确说"归档"**              |

### 8.4 归档命名规范

归档时保持原文件名，按以下结构存放：

```
归档文件/
├── 2026-09/
│   ├── 需求/
│   │   └── 需求-V0.1-001_废除中间表.md
│   ├── 缺陷/
│   │   └── 缺陷单-V0.1-001_Schema字段不匹配.md
│   └── 开发报告/
│       └── 开发报告-V0.1-001_废除中间表.md
└── 2026-10/
    └── ...
```

### 8.5 归档操作流程

1. **人类发起**：人类明确说"把XXX归档"或"归档任务卡T-001"
2. **AI执行**：AI将指定文档从活跃区移动到归档区对应月份目录
3. **确认回复**：AI回复"已归档至 `归档文件/YYYY-MM/类型/文件名`"
4. **禁止行为**：AI不得在人类未明确指令时自行归档任何文档

### 8.6 例外情况

以下文档**永不归档**，长期保留在活跃区：

- `AGENTS.md` 本身
- 正在使用的Schema规范文档
- 当前迭代的通用约定
